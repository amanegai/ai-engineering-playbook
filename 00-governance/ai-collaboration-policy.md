# AI 協業原則

## 1. 全体方針

- **AI が下書きを作成し、人が確認して実行**：AI は初稿や実装案を作り、人が意思決定と受け入れを行う
- **固定の入力/出力**：各 AI タスクは標準プロンプトと出力形式を使い、雑な対話による品質ばらつきを防ぐ
- **小さく前進**：大きなタスクは小分けし、1 ステップずつ検証してから次に進む
- **学びの回収**：プロジェクト完了後に、有効だったパターンやつまずきの記録を本リポジトリへ回収する

## 2. AI が単独で作業してよいもの

| 作業 | 説明 |
|------|------|
| 要件ドキュメントの初稿 | 口頭説明や議事録から構造化した要件を作る |
| 設計ドキュメントの草案 | 基本設計、詳細設計、API/DB 設計 |
| タスク分解 | Phase を具体的な開発手順へ分解する |
| コード実装 | 明確な設計と受け入れ基準がある前提でコードを書く |
| コードレビュー案 | チェックリストに沿って矛盾や抜け漏れを洗い出す |
| ドキュメント生成 | SETUP.md、API ドキュメント、コメント等 |
| テストケース草案 | メインフローと境界ケースのテスト観点一覧 |

## 3. 人の確認が必須のもの

| 作業 | 理由 |
|------|------|
| 要件範囲の確定 | AI による拡張や重要要件の見落としを防ぐ |
| 権限モデル設計 | 安全性に関わるため、必ず人が審査する |
| DB スキーマ変更 | 全開発者に影響するため、統一管理とレビューが必要 |
| API 契約の確定 | 多人数協業の契約で、変更コストが高い |
| 本番デプロイ設定 | 秘密情報、ネットワーク、データ安全性に関わる |
| 外部システム連携の方式 | 実運用の制約を把握する必要がある |
| UI/UX の最終判断 | ユーザー体験とブランド整合が必要 |

## 4. AI が直接決めてはいけないこと

- 本番環境の秘密情報（API Key、パスワード、接続文字列）
- データ削除、取り消し不能な操作
- OA システム等の既存プロジェクトの中核ロジックの変更（明確な依頼がある場合を除く）
- 技術スタックの勝手な選定（本リポジトリの標準に従う）

## 5. Cursor の使用モード

| モード | 適用場面 |
|------|---------|
| **Ask モード** | コード理解、方針の相談、review、質問 |
| **Agent モード** | ファイル作成/変更、コマンド実行、機能実装 |

推奨フロー：Ask モードで方針相談 → 確認後に Agent モードで実行。

## 6. AI 出力の受け入れフロー

```
AI が出力を作成
  ↓
acceptance-checklist に照らして自己チェック
  ↓
開発者レビュー（重点：範囲、命名、権限、境界ケース）
  ↓
OK なら次へ
NG なら指摘し、AI に修正させる
```

## 7. プロンプト利用ルール

- `04-ai-workflows/prompts/` の標準プロンプトを使い、場当たりで組み立てない
- プロンプト内で関連テンプレートや前提ファイルパスを参照する
- 各 AI タスクは「目的、範囲、やらないこと、受け入れ基準」を明示する
- 大タスクは小プロンプトに分けて段階的に実行する（1 回で Phase 全体を要求しない）
